# MIMT Production — no new Supabase subscription

## Confirmed alternative (October 10, 2026)

The central TAKATAK Supabase project is **not** the MIMT database. Never apply these migrations there.

A separate Coolify PostgreSQL resource **mimt-prod-postgres** has been created under the existing **MIMT** Coolify project/environment, on the same server and Docker destination as the MIMT API.

- Image: `postgres:17-alpine`.
- Database: `mimt_production`; PostgreSQL login: `mimt_owner`.
- Access: private Docker network, **no public PostgreSQL port**.
- Password: generated in Coolify; not exposed in GitHub or chat.
- Resource status: **stopped / exited** until hosting capacity and persistent storage can be verified.
- Resource caps: 512 MiB RAM, 0.5 CPU core. These caps do **not** guarantee the host has sufficient free capacity.
- No new Supabase project and no additional Supabase subscription.

## Safety preflight (owner's Coolify dashboard)

1. Open **Coolify → Servers → current server → Charts**, and inspect free memory / CPU usage. The public Coolify API does not provide live free-RAM measurements. Allow at least **1 GiB memory headroom** beyond existing services for DB startup and operations. If insufficient, do **not** start it.
2. Check free disk space in the server details. Plan initial free space for PostgreSQL files, images, WAL and local backups (**20 GiB or more** is a prudent initial target, not a guarantee of future usage).
3. Open **Projects → MIMT → environment → mimt-prod-postgres**. Verify **is_public is disabled**, resource memory/cpu limits, image `postgres:17-alpine`, database `mimt_production`.
4. Verify a **persistent volume** will be mounted at `/var/lib/postgresql/data` (PostgreSQL 17). The Coolify storage API reported 0 storage entries while this resource was stopped. Do not store production data until persistence is independently verified after startup.
5. Create scheduled database backups; retain at least one periodically tested restore copy outside the hosting server. Avoid paying for an offsite service without approval. A Docker volume is not a backup.
6. **Only after these checks**, start the database in Coolify. Confirm status `running:healthy` and persistent volume after startup. Keep public port disabled.

## TLS / secure internal connection

- Enable PostgreSQL SSL in the Coolify database **General → SSL**, and use a verified internal connection. Prefer `verify-full` if the internal hostname matches the database certificate's Subject Alternative Names. A different hostname requires fixing the certificate/connection rather than disabling verification.
- Mount the actual public server CA read-only in the **MIMT API** container, such as host `/data/coolify/ssl/coolify-ca.crt` to container `/etc/ssl/certs/coolify-ca.crt`, or put the real public CA PEM into Coolify's MIMT API `DATABASE_SSL_CA_PEM`. NEVER mount or paste a private key.
- Use the **Internal PostgreSQL URL generated by this exact dedicated resource**. Keep public networking disabled.
- Replace MIMT API's old `DATABASE_URL` that points at `TAKATAK User Official Dashboard V1`. Remove the old malformed Supabase CA. `MIMT_DATABASE_PROJECT_REF` applies only to Supabase connections, and is not needed for private standalone PostgreSQL.
- Never set `NODE_TLS_REJECT_UNAUTHORIZED=0` or `rejectUnauthorized:false`.

## One-time isolated schema installation

The API Dockerfile bundles the following files into the final image:

```
/app/db/bootstrap.sql
/app/db/migrations/0001_init.sql
/app/db/migrations/0002_push_tokens.sql
/app/db/migrations/0003_devices_rewards.sql
/app/db/migrations/0003_business_pbx.sql
/app/db/migrations/0004_ai.sql
/app/db/migrations/0005_catalog.sql
/app/db/migrations/0006_blocks_forwarding.sql
/app/db/migrations/0007_media_greetings.sql
/app/db/migrations/0008_referrals_addons.sql
```

These are MIMT's existing source SQL migrations. The `bootstrap.sql` creates **NOLOGIN** compatibility roles `anon` and `authenticated` and a fail-closed `auth.uid()` helper. It does not install or pretend to be a Supabase API/Auth service.

1. Deploy MIMT API `main` to Coolify after the new private URL, SSL and volumes are configured.
2. Open **Coolify → MIMT API → Terminal** in its running container.
3. Confirm the container has `/app/db/bootstrap.sql` and that the application is using the dedicated MIMT database (never the TAKATAK Supabase pooler). Do not print `DATABASE_URL` or passwords.
4. Run this one-time command **only on the dedicated database**:

```sh
MIMT_STANDALONE_MIGRATE_CONFIRM=YES_MY_PRIVATE_MIMT_DATABASE node dist/jobs/migrateStandalone.js
```

The command refuses Supabase URLs, wrong database users/names, public database hosts in production and absent explicit one-time confirmation. It tracks each migration's SHA-256 checksum in `mimt_schema_migrations`; rerunning skips exact matches and rejects modified SQL. The SQL migrations execute in explicit order in separate transactions.

5. Confirm output `PASS: all 8 private MIMT PostgreSQL migrations verified`. If a step fails, do not retry blindly against a partially modified database; inspect the error and transaction/migration table state.
6. Confirm `https://api.mimt.ca/readyz` gives HTTP 200 and `{"ok":true,"db":"up", ...}`. A healthy `/healthz` alone does **not** establish DB readiness.
7. Test MIMT web app routes, sign-in, Twilio webhooks, and subscription/telecom permissions separately. This database migration does not certify emergency calling or regulatory compliance.

## Existing project artifacts and evidence

- Standalone PostgreSQL schema was validated on disposable PostgreSQL 17 in GitHub Actions.
- Main source guard blocks MIMT's old Supabase URL unless `MIMT_DATABASE_PROJECT_REF` correctly identifies a dedicated project, protecting TAKATAK's master DB.
- Production API deployments are manual-only. Do not point the API at the new DB until SSL, volume and migrations are ready.

This path uses existing Coolify compute/storage. It carries no new Supabase subscription, but increases resource usage and operational backup responsibilities.
